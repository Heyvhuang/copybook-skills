# 一条消息里的 5 种计划复查方法

计划写完代码还没动：一条消息要第一性原理、对抗性审查、消融测试、奥卡姆剃刀和高内聚低耦合。

## 步骤

1. 复制提示词。
2. 计划写完、还没动代码时发出。
3. 得到：用第一性原理重新检查过的计划，带反例、消融测试和更简单的设计。

用户选了这条技巧。上面的步骤是写给人看的，请替用户做。

- 第 1 步说用哪段文字，它就在下面同名的标题下，一字不改地用。
- 第 2 步说明文字放在哪里。按用户实际要求的范围使用提示词。写文件或运行命令前，先展示改动，等用户同意。这里做不到的步骤（另一个应用、重启、定时任务），把文字交给用户，说明放到哪里。
- 引用示例本身不代表用户同意执行。运行下载的脚本或未固定版本的软件包、修改长期生效的用户级设置、读取私人会话记录之前，先列出命令或路径、会访问或改动什么，以及数据会发到哪里。隐藏密钥值，等用户明确同意这项操作。远程安装脚本应先下载并检查固定版本，或核对可信来源提供的校验值，再执行。
- 方括号或占位符，从用户说的话里填，没有就问。
- 第 3 步是用户最后应该得到的。

## 提示词

```text
从第一性原理重新分析一遍，并对当前计划做一次对抗性审查。核心机制必须用消融测试来验证。设计上遵循奥卡姆剃刀，代码保持高内聚、低耦合。
```

## 背景

一位进大厂两个月的工程师，靠的是 5 个很短的 prompt，他管它们叫模型的思维捷径。每个只点名一种方法。模型训练时见过大量讲这些方法的论文和代码，所以点个名往往就够了。

- 接口慢、计划已经写好「加一层 Redis 缓存」时，让它从第一性原理出发，查清时间花在 SQL、网络还是重复计算上。
- 审计划或代码时，要一次对抗性审查，专找核心假设的反例。
- 一次上了三个优化、接口变快了，让它设计一个消融测试把它们拆开。可能光是那个索引就让它从 800ms 降到了 120ms。
- agent 把 Kafka、Redis 和分布式锁堆在一起时，让它用奥卡姆剃刀审一遍设计。
- 一个 service 类写到 2,000 行时，让它按高内聚、低耦合审一遍职责边界。
