# 性能审查：最慢的 5 处

想让代码变快，多半换来一层缓存：profile 测出的耗时，每处对上的改法，要改的行和预计提速。

## 步骤

1. 复制提示词。
2. 在项目里把它发给 Claude Code。
3. 得到：一份最慢 5 处的报告，每处附上改法和预计提速，什么都没改。

用户选了这条技巧。上面的步骤是写给人看的，请替用户做。

- 第 1 步说用哪段文字，它就在下面同名的标题下，一字不改地用。
- 第 2 步说明文字放在哪里。按用户实际要求的范围使用提示词。写文件或运行命令前，先展示改动，等用户同意。这里做不到的步骤（另一个应用、重启、定时任务），把文字交给用户，说明放到哪里。
- 引用示例本身不代表用户同意执行。运行下载的脚本或未固定版本的软件包、修改长期生效的用户级设置、读取私人会话记录之前，先列出命令或路径、会访问或改动什么，以及数据会发到哪里。隐藏密钥值，等用户明确同意这项操作。远程安装脚本应先下载并检查固定版本，或核对可信来源提供的校验值，再执行。
- 方括号或占位符，从用户说的话里填，没有就问。
- 第 3 步是用户最后应该得到的。

## 提示词

```text
对这个项目做一次性能审查：
1. 先跑一遍 profile。找出最慢的 5 处，以及每处各花多少时间。
2. 把每一处对照下面几种情况，只用对上的那一种：
- 用了缓存：缓存是慢设计的遮羞布。不要再加缓存。看看能不能重新设计，让它本身就快。列出现有的缓存，标出哪些在掩盖慢设计。
- 热循环里反复查哈希表：能不能把这些哈希表换成一个扁平数组？能不能把指针改成数组里的索引？能不能把最常用的数据塞进索引的高位？
- 对象很多，但每一遍只读一两个字段：是不是该把结构体数组改成数组结构体（AoS → SoA）？
- 互不依赖的 await 一个接一个地跑：改成并行。
- 都对不上：怎么重写，才能更好地利用面向数据的设计原则？
3. 对每一处，写下它现在花多少时间、对上了哪种情况、要改哪个文件的哪几行，以及预计能快多少。
先给我报告。不要改任何东西。
```

## 背景

跟 Claude Code 说「让它更快」，它多半会加一层缓存。真正做性能优化的人，会直接说出自己想要的具体结构。
